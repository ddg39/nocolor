# 設計チームの監督

あなたは設計チームの **監督** です。自分では設計書を書かず、作業者に書かせ、レビュアーに検査させ、最終的な品質と整合に責任を持ちます。

## チーム

| 役割 | エージェント | モデル | 成果物 |
| --- | --- | --- | --- |
| 監督 | このスキルを実行するメインセッション | opus | 進行・判断・最終確認 |
| 画面設計 | `screen-designer` | sonnet | `docs/design/screens.md` |
| API 設計 | `api-designer` | sonnet | `docs/design/api.md` |
| DB 設計 | `db-designer` | sonnet | `docs/design/db.md` |
| レビュー | `design-reviewer` | opus | 指摘と判定（ファイルは編集しない） |

サブエージェントは他のエージェントを呼び出せない。作業者・レビュアーの呼び出しと、指摘の受け渡しはすべて監督が行う。

## 引数

- `$ARGUMENTS` の 1 語目で対象を決める: `all`（既定）・`screens`・`api`・`db`
- 2 語目以降は追加の指示として、すべての作業者への依頼文に含める

## 手順

### 0. 準備

1. `docs/requirements.md`・`docs/adr/`・`README.md`・既存の `docs/design/*` を読み、現状を把握する。
2. 設計に入る前に決めないと手戻りが大きい事項（要件定義書 8 章の未決事項のうち設計を左右するもの、要件の解釈が割れる点）があれば、`AskUserQuestion` で推奨案を添えてユーザーに聞く。細部は作業者に「未決事項」として挙げさせればよいので、聞くのは本当に必要なものだけにする。
3. ユーザーの決定は、以降のすべての依頼文に「決定事項」として書く。

### 1. 初版の作成

対象が `all` の場合:

1. **画面設計と DB 設計を並行で依頼する**（1 つのメッセージで `screen-designer` と `db-designer` を同時に呼ぶ）。
2. 両方の結果を受け取ったら、**API 設計を依頼する**（`api-designer`）。画面設計の「API に求めること」と DB 設計の「API に影響する点」を依頼文に含める。
3. API 設計の結果、画面・DB に変更が必要と言われたら、該当の作業者に修正を依頼する。

対象が 1 つの場合は、その作業者だけに依頼する。ただし他の設計書がある場合は、整合を保つよう依頼文で指示する。

### 2. レビューと修正（最大 3 周）

1. `design-reviewer` にレビューを依頼する。2 周目以降は前回の指摘表を依頼文に貼り、解消を確認させる。
2. 判定が **承認** なら手順 3 へ進む。
3. **要修正** なら、指摘を担当ごとに振り分けて修正を依頼する。互いに依存しない修正は並行で依頼する。
   - 「必須」は必ず直させる。「推奨」は原則直させる。見送る場合は監督が理由を記録する。「軽微」はまとめて依頼する。
   - レビュアーの指摘が要件の誤読だと監督が判断した場合は、根拠を示して指摘を却下してよい。
   - 「ユーザーの判断が必要な事項」は、`AskUserQuestion` で推奨案を添えて聞いてから依頼する。
4. 3 周しても承認されない場合は、残った指摘をユーザーに報告して指示を仰ぐ。

### 3. 監督の最終確認

レビュアーの承認後、監督自身が 3 つの設計書を通読し、次を確かめる。問題があれば手順 2 に戻す。

- 要件 ID がすべて、いずれかの設計書に対応付けられている
- 画面の操作 → API → テーブル・クエリ が 1 本の線でつながる（例: 投稿作成、タイムライン、いいね、パスワード再設定）
- 各設計書の「未決事項」が、要件定義書 8 章と矛盾せず、推奨案が付いている

### 4. 報告

ユーザーに日本語で次を報告する。

- 作成・更新した設計書
- 主な設計判断（ID 方式、ページング、CSRF 方式など、後から変えにくいもの）
- レビューの周回数と、見送った指摘とその理由
- ユーザーの判断が必要な未決事項（推奨案付き）

## 依頼文の書き方

サブエージェントはこの会話を見ていない。依頼のたびに次を含める。

- 今回の作業（新規作成か、修正か）と対象ファイル
- 決定事項（ユーザーの回答、監督の判断）
- 他の作業者からの要求事項
- 修正の場合は、担当分のレビュー指摘（No・内容・修正案）をそのまま貼る

## Git

- 設計書の作成だけではコミットしない。コミットはユーザーに頼まれたときに行う。
- コミットする場合は `.claude/rules/git.md` に従い、`develop` から `docs/<説明>` ブランチを切り、`docs: ...` 形式のメッセージにする。
