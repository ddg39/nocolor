# 要件定義書

## 1. 概要

### 1.1 目的

白黒（グレースケール）の画像のみを投稿できる SNS「nocolor」を提供する。色を排した表現に限定することで、構図・光・陰影で作品を見せ合える場をつくる。

### 1.2 前提・制約

- 公開リポジトリとして公開し、**Docker（docker compose）のみで全機能が動作する**こと。ホスト側に Go や Node.js などのインストールを要求しない。
- 外部の SaaS（メール配信サービス、クラウドストレージなど）に依存しない。必要なものはすべてコンテナとして同梱する。
- 使用技術は [README.md](../README.md) に定めたものとする。

### 1.3 用語

| 用語 | 意味 |
| --- | --- |
| 白黒画像 | 全ピクセルで R・G・B の値がほぼ等しい画像（グレースケール）。判定方法は 4.3 を参照 |
| 投稿 | 白黒画像 1 枚と任意のキャプションの組 |
| 全体タイムライン | 全ユーザーの投稿を新着順に並べた一覧 |
| フォロー中タイムライン | 自分がフォローしているユーザーの投稿を新着順に並べた一覧 |
| 本登録 | メールアドレスの確認が完了した状態 |

## 2. スコープ

### 2.1 MVP に含める

- アカウント登録（メール確認あり）・ログイン・ログアウト
- パスワード再設定（メール経由）
- 投稿の作成・閲覧・削除
- いいね
- フォロー
- タイムライン（全体／フォロー中をタブで切替）
- プロフィールの表示・編集

### 2.2 MVP に含めない（将来の検討事項）

- コメント
- 通報、管理者機能、ブロック、ミュート
- 投稿の編集（キャプションの後からの変更）
- 1 投稿に複数枚の画像
- 検索、ハッシュタグ
- 通知
- メールアドレスの変更、退会
- バックエンドでのカラー画像の白黒変換（変換はフロントエンドのみで行う）

## 3. 利用者と権限

| 操作 | 未ログイン | ログイン済み |
| --- | --- | --- |
| 全体タイムラインの閲覧 | ○ | ○ |
| フォロー中タイムラインの閲覧 | × | ○ |
| 投稿詳細・プロフィールの閲覧 | ○ | ○ |
| 投稿の作成・削除 | × | ○（削除は自分の投稿のみ） |
| いいね・フォロー | × | ○ |
| プロフィールの編集 | × | ○（自分のみ） |

- 未ログインで要ログインの操作をしようとした場合は、ログイン画面へ誘導する。
- 管理者ロールは MVP では設けない。

## 4. 機能要件

### 4.1 アカウント

| ID | 要件 |
| --- | --- |
| ACC-01 | メールアドレス・ユーザー名・パスワードを入力してアカウントを仮登録できる |
| ACC-02 | 仮登録時に確認メールを送信する。メール内のリンクを開くと本登録となる |
| ACC-03 | 確認リンクの有効期限は 24 時間とする。期限切れまたは未着の場合は確認メールを再送できる |
| ACC-04 | 本登録が完了していないアカウントはログインできない。ログインを試みた場合は確認メールの再送を案内する |
| ACC-05 | 一定時間内に本登録されなかった仮登録は破棄し、同じメールアドレス・ユーザー名で再登録できるようにする（期限は 7 日） |
| ACC-06 | ユーザー名（またはメールアドレス）とパスワードでログインできる |
| ACC-07 | ログアウトできる |
| ACC-08 | パスワードを忘れた場合、メールアドレスを入力すると再設定用リンクを送信する。リンクの有効期限は 1 時間とし、一度使うと無効になる |
| ACC-09 | パスワード再設定画面では、入力されたメールアドレスが登録済みかどうかを画面上で区別しない（アカウントの存在を推測させない） |

入力規則:

| 項目 | 規則 |
| --- | --- |
| ユーザー名 | 3〜20 文字、英小文字・数字・`_` のみ。一意。登録後は変更不可（プロフィール URL に使うため） |
| メールアドレス | 形式チェックを行う。一意 |
| パスワード | 8〜32 文字。英字と数字をそれぞれ 1 文字以上含む |

### 4.2 プロフィール

| ID | 要件 |
| --- | --- |
| PRF-01 | ユーザーごとにプロフィールページ（`/users/{ユーザー名}`）を持つ |
| PRF-02 | プロフィールページには、アイコン・表示名・ユーザー名・自己紹介・投稿数・フォロー数・フォロワー数・投稿一覧（新着順）を表示する |
| PRF-03 | 自分の表示名（1〜30 文字）と自己紹介（0〜160 文字）を編集できる |
| PRF-04 | 自分のアイコン画像を設定・変更・削除できる。アイコンも投稿と同じく、フロントエンドで白黒に変換してプレビューし、バックエンドで白黒かを検査する（4.3 の PST-04・PST-05 と同じ）。未設定時は既定のアイコンを表示する |
| PRF-05 | フォロー一覧・フォロワー一覧を表示できる |

### 4.3 投稿

| ID | 要件 |
| --- | --- |
| PST-01 | 白黒画像 1 枚と任意のキャプション（0〜500 文字）で投稿できる |
| PST-02 | 投稿できる画像は JPEG・PNG・WebP、ファイルサイズ 10MB 以下とする。上限は環境変数で変更できる |
| PST-03 | アニメーション画像（アニメーション PNG / WebP）は受け付けない |
| PST-04 | フロントエンドは、ユーザーが選んだ画像を白黒（グレースケール）に変換し、変換後の画像をプレビュー表示する。カラー画像も選択でき、投稿時には変換後の画像をアップロードする |
| PST-05 | バックエンドは受け取った画像の全ピクセルを検査し、白黒画像でなければエラーとして投稿を拒否する（HTTP 400）。白黒への変換はバックエンドでは行わない。拒否時は「白黒画像のみ投稿できます」とわかるメッセージを表示する |
| PST-06 | 投稿は作成後に編集できない。自分の投稿は削除できる。削除時は MinIO 上の画像も削除する |
| PST-07 | 投稿詳細ページ（`/posts/{投稿ID}`）で、画像・キャプション・投稿者・投稿日時・いいね数を表示する |
| PST-08 | 保存時に EXIF などのメタデータ（位置情報を含む）を取り除く |

白黒判定の仕様:

- 各ピクセルについて `max(R, G, B) - min(R, G, B)` を求め、これが許容値以下であれば灰色とみなす。
- JPEG は圧縮でわずかに色ずれが生じるため、許容値を設ける。既定値は実装時の検証で決め、環境変数で変更できるようにする。
- 透明度（アルファチャンネル）は判定に使わない。完全に透明なピクセルは判定対象から除く。

### 4.4 いいね

| ID | 要件 |
| --- | --- |
| LIK-01 | 他人および自分の投稿にいいねできる。1 ユーザーにつき 1 投稿 1 回まで |
| LIK-02 | いいねを取り消せる |
| LIK-03 | 投稿ごとにいいね数を表示する。ログイン中は自分がいいね済みかどうかもわかるようにする |

### 4.5 フォロー

| ID | 要件 |
| --- | --- |
| FOL-01 | 他のユーザーをフォローできる。自分自身はフォローできない |
| FOL-02 | フォローを解除できる |
| FOL-03 | フォローは承認不要（相手の許可なしに成立する）とする |

### 4.6 タイムライン

| ID | 要件 |
| --- | --- |
| TML-01 | ホーム画面に「全体」「フォロー中」の 2 つのタブを設け、切り替えられる |
| TML-02 | 「全体」タブには全ユーザーの投稿を新着順に表示する |
| TML-03 | 「フォロー中」タブには、フォローしているユーザーと自分の投稿を新着順に表示する |
| TML-04 | 未ログイン時は「全体」タブのみ表示する |
| TML-05 | 下までスクロールすると続きを読み込む（無限スクロール）。ページングはカーソル方式とし、読み込み中に新しい投稿が増えても重複・欠落しないようにする |
| TML-06 | 一覧では縮小画像（サムネイル）を表示し、詳細ページで元のサイズの画像を表示する |

## 6. 非機能要件

### 6.1 動作環境・構成

- `docker compose up` だけで、フロントエンド・バックエンド・MySQL・MinIO・メールサーバーが起動すること。
- 開発環境のメール送信先には、送信内容をブラウザで確認できる SMTP サーバーのコンテナ（例: Mailpit）を使う。本番相当の環境では環境変数で任意の SMTP サーバーに切り替えられること。
- 設定値（DB 接続情報、MinIO の認証情報、SMTP 設定、画像サイズ上限、白黒判定の許容値など）は環境変数で与える。秘密情報はリポジトリに含めず、`.env.example` を用意する。
- DB スキーマは golang-migrate で管理し、起動時またはコマンド 1 つでマイグレーションを適用できること。
- 対応ブラウザは Chrome・Firefox・Safari・Edge の最新版。スマートフォンの画面幅でも利用できること（レスポンシブ対応）。

### 6.2 セキュリティ

- 認証はセッション + Cookie で行う。Cookie には `HttpOnly`・`SameSite=Lax` を付け、HTTPS 環境では `Secure` も付ける。
- セッションの有効期限は 30 日とし、ログアウト時・パスワード再設定時に破棄する。
- 状態を変更するリクエストには CSRF 対策を行う。
- パスワードは bcrypt などの適切なハッシュ関数で保存する。
- メール確認・パスワード再設定のトークンは推測困難な乱数とし、DB にはハッシュ化して保存する。
- ログインと各種メール送信には試行回数の制限を設ける。
- アップロードされた画像は拡張子ではなくファイルの中身で形式を判定する。
- 画像の配信時は、ユーザーがアップロードしたファイルが HTML やスクリプトとして解釈されないようにする（`Content-Type` の固定、`X-Content-Type-Options: nosniff`）。

### 6.3 性能

- 一覧 API は 1 回あたり 20 件程度を返し、通常の負荷で 500ms 以内に応答すること。
- フロントエンドでの白黒変換とプレビュー表示は、10MB の画像でも画面が固まらない程度の時間で完了すること。
- 投稿時の白黒判定とサムネイル生成は、10MB の画像でも数秒以内に完了すること。

### 6.4 品質・運用

- バックエンドの白黒判定・認証まわりにはユニットテストを書く。
- エラー時は、利用者に原因がわかるメッセージを日本語で表示する。

## 7. データ（概要）

詳細な設計は別途行う。主な要素は以下のとおり。

| エンティティ | 主な項目 |
| --- | --- |
| ユーザー | ID、ユーザー名、メールアドレス、パスワードハッシュ、表示名、自己紹介、アイコンのオブジェクトキー、本登録日時、作成日時 |
| 投稿 | ID、投稿者 ID、画像のオブジェクトキー、サムネイルのオブジェクトキー、キャプション、作成日時 |
| いいね | ユーザー ID、投稿 ID、作成日時（ユーザー ID と投稿 ID の組で一意） |
| フォロー | フォローする側の ID、される側の ID、作成日時（組で一意） |
| セッション | セッション ID、ユーザー ID、有効期限 |
| メール確認トークン | トークンのハッシュ、ユーザー ID、有効期限 |
| パスワード再設定トークン | トークンのハッシュ、ユーザー ID、有効期限、使用済み日時 |

画像本体は MinIO に保存し、DB にはオブジェクトキーのみを持つ。
