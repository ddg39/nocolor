# ADR 001: 配信構成

- ステータス: 承認
- 日付: 2026-10-26

## 背景

[要件定義書](../requirements.md) の未決事項として、フロントエンド・バックエンド・投稿画像をどのように配信するかが残っていた。決めるにあたって、次の条件を満たす必要がある。

- Docker（docker compose）のみで全体が動くこと。
- 認証はセッション + Cookie で行う。Cookie には `SameSite=Lax` を付け、CSRF 対策も行う。
- 投稿画像は MinIO に保存する。画像は未ログインのユーザーも閲覧できる公開情報である。
- ユーザーがアップロードしたファイルを、HTML やスクリプトとして解釈させてはならない。
- 開発中はフロントエンドの変更をすぐに確認できること（HMR）。

## 決定

nginx をリバースプロキシとして唯一の入口に置き、フロントエンド・API・画像を **同一オリジン** で配信する。

```
ブラウザ
  └ nginx :80（外部に公開するのはこのポートのみ）
      ├ /api/*     → backend（Echo）
      ├ /images/*  → MinIO（公開読み取り用のバケット）
      └ /*         → フロントエンド
                      本番: ビルド済みの静的ファイルを nginx が直接配信
                      開発: Vite 開発サーバーへプロキシ
```

### パスの割り当て

| パス | 転送先 | 補足 |
| --- | --- | --- |
| `/api/*` | backend | `/api` を付けたまま転送し、Echo 側のルートも `/api` から始める |
| `/images/*` | MinIO | 投稿画像・サムネイル・アイコンを置くバケットに転送する |
| `/*` | フロントエンド | 該当するファイルがなければ `index.html` を返す（SPA のクライアント側ルーティングのため） |

### 画像の配信

- 画像用のバケットには匿名での読み取り（`GetObject`）のみを許可する。オブジェクトの一覧取得と書き込みは許可しない。
- 書き込み・削除は backend だけが MinIO の認証情報を使って行う。
- MinIO の API ポートと管理画面は外部に公開しない。開発用の compose でのみ、管理画面をホストに公開してよい。
- nginx で画像のレスポンスに `X-Content-Type-Options: nosniff` を付ける。`Content-Type` は、backend がアップロード時に検査した画像形式をもとに設定し、それ以外の値は受け付けない。
- 投稿は編集できず、アイコンの変更時は新しいキーで保存する。同じキーの中身が変わることはないため、画像には長期間のキャッシュ（`Cache-Control: public, max-age=31536000, immutable`）を設定する。
- オブジェクトキーには推測しにくい ID（UUID など）を使う。

### アップロードサイズ

- nginx の `client_max_body_size` は、画像サイズの上限（既定 10MB）にフォーム部分の余裕を加えた値にする。上限は環境変数から設定する。

### 開発環境と本番環境

compose ファイルを分け、nginx の `/` の転送先だけを切り替える。それ以外の URL 構成は同じにする。

| | 開発 | 本番 |
| --- | --- | --- |
| `/` | Vite 開発サーバーへプロキシ（HMR 用の WebSocket も転送する） | ビルドした静的ファイルを nginx から配信 |
| ソースコード | ボリュームでマウントする | イメージ内でビルドする（マルチステージビルド） |
| メール | Mailpit | 環境変数で指定した SMTP サーバー |
| MinIO の管理画面 | ホストに公開する | 公開しない |

### HTTPS

- TLS の終端は nginx の前段（ホスト側のリバースプロキシやロードバランサー）で行う想定とし、このリポジトリでは扱わない。
- backend は `X-Forwarded-Proto` を見て、HTTPS のときに Cookie へ `Secure` を付ける。

## 検討した別案

### Echo がフロントエンドの静的ファイルも配信する

ビルドしたファイルを Go のバイナリに埋め込めばコンテナは減る。しかし、フロントエンドを変えるだけでも backend のビルドが必要になる。また、開発時の HMR を別の仕組みで用意する必要があるため採用しない。

### フロントエンドと API を別オリジンにし、CORS で許可する

CORS の設定に加え、Cookie を送るための `credentials` の扱いや、`SameSite` の調整が必要になる。設定を誤ったときにセッションが漏れる危険が増えるため採用しない。

### 画像を Echo 経由で配信する

アクセス制御やヘッダーを自由に変えられる。ただし、画像はすべて公開情報なのでアクセス制御は不要である。画像の転送で backend の負荷が増えるため採用しない。

### 署名付き URL でブラウザから MinIO に直接アクセスさせる

MinIO を外部に公開する必要がある。また、URL に期限があるためキャッシュも効きにくい。公開画像に対しては利点が小さいため採用しない。

## 影響

- ブラウザから見えるオリジンは 1 つになるので、CORS の設定は不要になる。Cookie は `SameSite=Lax` のまま使える。
- フロントエンドから API を呼ぶときは `/api/...` の相対パスを使い、ホスト名を設定に持たない。
- 画像の URL は `/images/{オブジェクトキー}` の形にし、backend はこの形式で API のレスポンスに含める。
- nginx の設定ファイルは開発用と本番用の 2 つを管理する。
- MinIO の起動時にバケットを作成し、匿名読み取りのポリシーを設定する初期化処理（`mc` を使う使い捨てのコンテナなど）が必要になる。
